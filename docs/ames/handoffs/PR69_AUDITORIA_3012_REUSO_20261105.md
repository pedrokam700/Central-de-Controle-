2. O fluxo CLEAN 3074 possui checkpoint por PCBA no disco e retoma se o **hash da lista de registros é idêntico**. O modo `repair_partials` altera a lista (somente PCBAs pendentes) e, portanto, muda o hash; não transferia as leituras verificadas para o novo checkpoint. Assim, mesmo uma recuperação *seletiva* podia repetir consultas 3074 já aprovadas.
3. `agent_entry.py` consultava apenas o último `integrated_v016` ao recompor uma tentativa parcial e **só fazia união se todas as PCBAs anteriores ainda constassem no filtro corrente**. Um lote menor ou uma captura posterior de outra linha impedia a união; podia ocultar na leitura evidência válida de uma revisão anterior do mesmo snapshot. Não se deve resolver isso misturando outras linhas/dias; a reconstrução por linha usa a função já existente `recover_snapshot_line`, que exige correspondência exata de PCBA/código/hora/linha.
4. A 3022 coletava todas as respostas MES **em memória** e só depois fazia a etapa B de persistência/correlação. Uma interrupção entre A e B descartava da memória respostas já consultadas. O callback só escrevia metadados de progresso, não as linhas confirmadas. A 3012 já possuía cache por SN/trecho, mas sua interrupção após duas falhas é um circuito de proteção para evitar uma hora de consultas sem confirmação; exige diagnosticar o erro de contrato da versão `48959f0` antes de reabrir o escopo inteiro.
